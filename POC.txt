Стратегія локаторів: Xpath "head-tail" з пошуком по тексту
1. Легкість масштабування

a. Пошук елементів по тексту. Додаючі нові тексти в сonstants.py можна покрити нові елементи на будь-якій сторінці
b. Типові локатори для типових головних компонентів (head). MainForm, Footer - для типової сторінки авторизації є head, отже для нових пейджів авторизації (або інших, що їх використовують) тести можна скопіювати як є.
c. Частина елементів є універсальною і описана в base_elements.py: ButtonText, FieldText etc, які додаються до head як конструктор tail. Наприклад head //form, tail //button. Отже щоб описати новий компонент в ПО достатньо використати існуючі tail.
d. Параметризація. сonstants.py можна використати для фікстур і передавати в тест по аналогії з драйвером. Наприклад для валідаційних помилок, передав 2 фікстури - дані та помилку.

2. Легкість підтримки
a. language and framework netrual. Пошук елементів по тексту вимагає коригування лише текстів констант або заміну констант для конкретного теста без знання мови програмування або особливостей фреймворка.

b. SOLID (S): кожна функціональність описана в окремому методі: button_text(), fields etc.
c. SOLID (L): локатор використовується в методах батьківського класу base_web.py  - click(), type() etc, а також в методах ПО для формування повного локатору button_text() etc 
d. SOLID (I): кожний компонент - це окремий класс із визначеною функціональністю. Функціональність декомпозована до мінімального ріня. Приклад: DisplayLanguage вибір язика - клас, що може бути розширений пошуком по тексту, таким чином треба буде додати метод field_text()
e. SOLID (D): побудова локатору в ПО кожному класі не вимагає змін в базовому класі взаэмодії з ним в base_web.py
f. Легкий дебаг. Кастомізований вивід помилок в base_web.py - назва классу, значення тексту в аргументі функції та повний локатор
